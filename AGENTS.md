# Working on Roslynk

This is a source-based implementation guide for future changes. Paths below are relative to the repository root unless a section says otherwise. Re-check the affected implementation before changing it; this guide describes the architecture and its current limits, not a substitute for the source.

## Start here

- The solution is `Source/Morris.Roslynk.slnx` (not under `Source/App`).
- Read `git status` before editing and preserve unrelated work.
- When Roslynk is connected, use its semantic tools for compiled C#, Razor and CSHTML: open the solution, use `get_members`/`get_symbol_body` to inspect implementations, and use reference/caller queries for impact analysis. Follow `skills/roslynk/SKILL.md` for routing; each tool's contract lives in its `[Operation]` description (copied from its C# method's `[Description]`) and is published in MCP metadata. Retry `Indexing` while loading; do not manually reload for ordinary source edits.
- Batch related read-only questions with `multi_query`. Re-query after writes. A running Roslynk server can inspect edited source, but editing this repository does **not** replace the server's executing implementation; run tests against the checkout to validate new behavior.
- Use normal file tooling for non-source configuration, documentation, and new-file creation. Roslynk's patch tool only edits existing files, and its plain-text fallback is rooted at the solution directory (`Source`), not the repository root.
- The most important seams are `RoslynInstance`, `SolutionModel`, `ApplyPipeline`, `AtomicFileWriter`, `SolutionFileSync`, and the internal cores used by `MultiQueryCatalog`.

## Required workflow for feature and tool changes

- When creating a new read-only tool, assess whether it is a candidate for `multi_query` and **ask the user whether to include it**, unless the user's request already explicitly says to add the tool to `multi_query` (then include it without asking). Otherwise do not silently include or exclude it. Continue independent implementation work while that choice is pending; if included, implement the pinned-model core, catalog/enum integration and relevant tests described below.
- Add every new feature and feature change to the `# Unreleased` section at the top of `releases.md`. Create that section at the top if it is missing, preserving existing release history. Each addition is a terse one-line bullet ending with `(Fixes #xx)`, where `xx` is the GitHub issue number, e.g. ``- New `get_callees` tool: the inverse of `get_callers` (Fixes #58)``. Detail belongs in the skill/tool docs, not in `releases.md`. If the issue number is unknown, ask the user.
- Documentation ownership: routing guidance lives in the roslynk skill (`skills/roslynk/SKILL.md`); shared workflows live in `McpServerRegistration.Instructions` (`Morris.Roslynk.Cli/Hosting`) as MCP server instructions; each tool's complete contract lives in its C# method's `[Description]` attribute, copied verbatim into its `[Operation]` description, which is what MCP metadata and `--capabilities` publish; its title is `[DisplayName]` on the request, equal to the method's `[McpServerTool(Title)]`; parameter contracts stay in code as `[Description]` attributes on parameters, with identical parameter contracts reusing `ParameterDescriptions`. Server instructions carry shared conventions once; tool descriptions contain only their own contracts. When a tool's contract or behavior changes, update its method description in the same change (and `SKILL.md` when routing changes), and check for contradictory or obsolete copies of the guidance.

## Lifecycle, snapshots and ordering

Sources: `Infrastructure/Lifecycle/{InstanceRegistry,RoslynInstance,SolutionModel,WriteResult,SemaphoreSlimReadWriteLock}.cs` under the core project.

`InstanceRegistry` owns a concurrent dictionary of lazy `RoslynInstance`s keyed by normalized solution paths (`SolutionKey`). Key comparison is case-insensitive on Windows/macOS, ordinal on other platforms. Do not invent a second registry or cache keyed by an unnormalized path.

- `GetOrBegin` supports nonblocking open: create/start the initial load, or start a dirty rebuild while returning the instance.
- `GetOrBeginAsync` is the normal data-tool entry point. It waits up to the registered `LoadWaitTimeout` (default 30 s; the app reads `Roslynk:LoadWaitSeconds`) for an in-flight initial load, joining that one load, and joins/starts a dirty rebuild. Its cancellation token cancels the wait, not the shared load. When the timeout elapses first it returns the instance with no snapshot, so a tool must still handle a null `model.Solution` as `Indexing` (`Error.Indexing(instance.LoadedProjects)` carries `projects=loaded/?`). The app's handlers pass the call's token (`OperationHandler.ReadAsync`), so a cancelled CLI or MCP call stops waiting at once.
- `SolutionKey.SolutionId` is the echoed handle: the absolute path with forward slashes, reusable verbatim in JSON; `SolutionKey.For` accepts either slash form.
- `GetOrAddAsync` waits for initial readiness and has a different dirty path that closes/recreates the instance; it is useful in tests, not interchangeable with the normal data-tool path.
- Instances track access for idle eviction and own the workspace, watcher, queue and cancellation lifetime.

`SolutionModel` is a published immutable wrapper containing status, optional Roslyn `Solution` and fault message. Each new wrapper has a fresh GUID `Id`, even when it contains the same `Solution`. This is a **publication generation**, not a content hash or Roslyn document version. Diagnostics status transitions can also change it.

`RoslynInstance.CurrentModel` uses `Volatile.Read`; publication uses `Volatile.Write`. `ReadModelAsync` briefly acquires a read lock, captures one model, and releases the lock. A reader starting during a locked write waits for publication, then performs semantic work against its captured immutable snapshot without holding the lock. Do not repeatedly consult `CurrentModel` halfway through a logical read or combine symbols/trees from different solutions.

Writes and diagnostics run on an unbounded channel with one consumer:

1. `EnqueueWriteAsync` queues a transform receiving the latest `Solution` when it executes.
2. Under the write lock, `RunWriteAsync` publishes `Updating`, invokes the transform, regenerates the Razor output the transform's changes affect (`RazorDocumentGenerator.RegenerateForChangesAsync`, not cancellable because the transform may already have written to disk), then publishes the result as `Ready`. This is the only place writes regenerate Razor: watcher folds, `ApplyPipeline` and `apply_patch` all rely on it, so no write publishes generated documents that disagree with its sources.
3. It marks diagnostics needed and clears the diagnostics cache, unless the transform returned the very `Solution` it was given (a no-op fold), in which case nothing is regenerated either. On transform failure it republishes the previous solution and faults that work item's completion; subsequent work must still run.
4. `WriteResult` contains the updated solution and changed physical paths. Watcher folds use an empty path list because disk was already edited.

Diagnostics requests are queued after pending writes; nothing queues diagnostics in the background. A caller that cancels stops waiting at once, even behind a long write, and its queued build is skipped (`RequestDiagnosticsAsync` cancels the returned task from the token; the consumer drops an item whose completion is already done). Compilation runs against a captured solution without holding the read lock, so semantic readers can continue. The instance cache is keyed by diagnostics mode and invalidated by writes/rebuilds; below it, `DiagnosticsService` memoizes per project (see Diagnostics). `DiagnosticsResult` includes the solution actually compiled: use that solution for mapping diagnostics, not whichever solution happens to be current later.

Rebuilds load a replacement workspace in the background. `RebuildGate` and `RebuildInFlight` coalesce callers. **Both successful rebuild publication and failure publication go through the same channel as incremental writes**, with the write lock protecting the swap. Preserve this ordering; direct publication can race a queued fold and lose an update. Rebuild completion reattaches watchers and disposes the previous workspace.

### Snapshot details to verify when extending lifecycle behavior

- `CurrentModel` access itself does not wait for an active writer; `ReadModelAsync` is the fenced read API. Several existing write tools capture `CurrentModel` directly.
- No MSBuild project properties are captured. `MSBuildWorkspace` evaluates projects out of process in its BuildHost, so `Microsoft.Build` is never loaded in Roslynk and in-process `ProjectInstance` evaluation is unavailable. Derive per-project build facts from the Roslyn `Project` itself (`CompilationOutputInfo`, `ParseOptions`, `AnalyzerOptions`), which every publication carries.
- A failed operation may publish a new model ID even though its source content did not change. Do not use generation equality as text equality.

## Disk writes: preserve all layers of protection

Sources: `Infrastructure/Writing` and `Features/Patching/ApplyPatch/ApplyPatchTool.cs`.

Semantic edits normally compute an immutable updated solution and call `ApplyPipeline.ApplyAsync`:

- The pipeline enqueues the operation on `RoslynInstance`, so validation and persistence execute under the single writer.
- The transform receives the latest solution, but `updated` was computed by the caller. Pass the snapshot it was computed from as `ApplyAsync(instance, updated, basedOn: solution, ...)`: inside the queue, `RebaseAsync` replays only the documents `updated` changed relative to `basedOn` onto the latest `current`, and throws `StaleWriteException` if an intervening publication (watcher fold or another write) changed any of those documents. Intervening edits to other documents are kept, not reverted. Without `basedOn` (the older overload), `updated` is persisted as-is and can silently revert an intervening publication. New write tools must pass `basedOn` and test the intervening-edit case.
- `BuildWritesAsync` enumerates changed ordinary and additional documents. Every physical path is written once, even if multiple target frameworks/projects share it. The computation must therefore update every document sharing that path consistently.
- Before any file is written, each loaded text is compared with current disk text using `FileHash` (SHA-256). A mismatch throws `StaleWriteException`. Additional documents, including Razor source, receive this check too.
- Generated paths ending in `.g.cs` are excluded from persistence. This is a broad suffix rule, not just a Razor check.
- `GetChangedFilePaths` is the preview seam. It does not perform the complete disk stale validation. `checkOnly` must not publish or write changes.
- The pipeline covers changed documents, not arbitrary project/file additions or removals. Do not assume all Roslyn `SolutionChanges` can be persisted through it.

`AtomicFileWriter` stages the whole batch into sibling `<path>.roslynk.tmp` files, then commits each with `File.Replace(temp, target, <path>.roslynk.bak)`. If a replacement fails, it attempts to restore already committed files from backups. Commit cleanup attempts to delete temp/backup siblings. Preserve the two public suffix constants because the watcher filters them.

Be precise about the guarantee: individual replacements are atomic, and the code implements rollback across a batch; this is not a filesystem transaction visible atomically to external readers or crash recovery. Staging happens before the commit try/finally, so a staging failure/cancellation can leave temp files. Rollback can itself fail, and there is no cross-process lock between disk validation and replacement. Do not strengthen these claims in tool documentation without changing implementation and testing failure cases.

Encoding is path-specific: `AtomicFileWriter` accepts an explicit encoding and defaults to UTF-8 without BOM. `FileEncoding.Detect` maps a file's UTF-8/UTF-16 BOM (or its absence) to the encoding to write it back with, and both write paths pass that to `PendingWrite`: `ApplyPipeline` when it re-reads each file for its stale check, decoding leniently as `File.ReadAllText` does, and `ApplyPatchTool`, which decodes strictly so a BOM-less file that is not valid UTF-8 is rejected as not text. Keep the two decoding policies distinct.

### Patch-specific path

`ApplyPatchTool` uses `UnifiedDiffParser` and `PatchApplier`, then queues its own transform using `AtomicFileWriter` rather than `ApplyPipeline`. It computes hunks against **current disk text**, with optional `baseVersions` checked using `FileHash.Of(text)`. Thus an omitted version is not equivalent to the semantic pipeline's loaded-text guard.

Hunks are content-anchored and must match uniquely; line numbers are not authoritative. Existing text files are supported; creation/deletion and binary content are rejected. Model paths are resolved before the solution-contained plain-text fallback, so inspect resolution carefully for linked files. Plain-text fallback rejects `bin`/`obj` and paths outside the solution directory. Encoding detection and path/version normalization are part of the contract.

After persistence, it updates all matching ordinary/additional documents in the latest solution. Plain files are disk-only. Build inputs and direct Razor patches can still require the watcher's dirty rebuild to refresh derived state.

### Existing guard limitations

All semantic write tools (`apply_code_action`, `apply_code_fix`, `extract_method`, `change_signature`, `rename_symbol`, `rename_parameter`, `remove_unused_usings`) pass `basedOn`. During rebase, generated `.g.cs` documents are never a conflict: if one was regenerated since the edit was computed, the regenerated text is kept. Also, `StaleWriteException` is an ordinary exception: the general MCP wrapper maps uncaught exceptions to `Faulted`; it does not automatically translate this type to `Stale`. When adding a write tool, deliberately format its stale failure and test the public response. Do not copy an older caller assuming it exercises every protection.

## File watching and freshness

Sources: `Infrastructure/Watching/{SolutionFileWatcher,SolutionFileSync}.cs`.

`SolutionFileWatcher` debounces events for 250 ms, batches distinct paths, forwards both old and new paths for renames, and hands each batch to `SolutionFileSync.OnFilesChangedAsync`, which folds everything foldable in the batch as one write (a save-all or branch switch compiles and regenerates once). It reports a directory's own creation, rename and deletion (`NotifyFilters.DirectoryName`; a moved directory raises no events for its files) and drops a directory's `Changed` events, which only echo a write inside it. Project directories are watched recursively; linked source/additional files and tracked ancestor build files can add shallow watches outside them. Watchers are reconstructed after a reload.

`SolutionFileSync` owns the classification rules:

- Ignore `bin`, `obj`, `.roslynk.tmp` and `.roslynk.bak` centrally, including direct calls that bypass the watcher adapter.
- An edit to a known file folds the new text into every document and additional document at that path (a `.cs` file can be both a compile item and an analyzer additional file); unchanged text is ignored, avoiding feedback from the server's own writes. The fold compares against the latest snapshot inside the queue, so an event that raced the server's own write changes nothing: replacing a text with an equal one would still fork every compilation downstream. Razor regeneration follows from the write (see Lifecycle): for a changed `.razor`/`.cshtml`, an added or removed document, a changed generated document, or a C# tree that is not top-level equivalent (`IsEquivalentTo(topLevel: true)`), since method bodies and initializers never reach generated code.
- Files inside a project directory's dot-folders (`.git`, `.vs`, `.idea`) or `node_modules` are ignored, matching the SDK's own default item excludes; build files there still count. The check is relative to each project directory, so a solution that itself lives under a dot-folder is unaffected.
- A changed `.razor`/`.cshtml` folds in place when `RazorGenerationState` covers its projects, and marks dirty otherwise (nothing else would regenerate it). Other additional documents (source generator inputs) fold in place too; Roslyn reruns the generators on the next compilation.
- A deleted compiled document is removed in place; a deleted additional document marks dirty. New `.cs` files can be folded into owning default-glob projects; explicit compile-item cases mark the instance dirty for MSBuild reevaluation.
- Default-glob detection currently uses project-file text heuristics, not full MSBuild item evaluation. Treat unusual conditions, exclusions and nested projects carefully.
- Build files (`.csproj`, `.vbproj`, `.fsproj`, `.props`, `.targets`, `.sln`, `.slnx`, `.ruleset`, `.globalconfig`, `.editorconfig`, `global.json`, `NuGet.config`) use content baselines to distinguish edits from touches.
- Roslyn sees only compile items, additional files and analyzer config, and the model lists every one it loaded, so an unknown existing file (content, embedded resources, a weaver's `.csv`) is ignored. `CouldChangeBuildInputs` marks dirty only for what may change membership: a deleted known file, a vanished directory of loaded files, a directory inside a project that is not a dot-folder or `node_modules` and holds no loaded documents yet (created, moved in or renamed), or a new file whose extension a glob may add (`.razor`, `.cshtml`, or that of an already loaded additional file). A first file of a custom `AdditionalFiles` glob whose extension nothing loaded uses yet is missed. Directory events outside project directories (the solution folder's `.git`) are ignored. Dirty rebuild is lazy and coalesced on subsequent use.
- `bin`/`obj` are ignored. Analyzer DLLs a load tracks are kept fresh by `TrackedAnalyzers` instead (below); a rebuilt NuGet or out-of-solution analyzer DLL that resolved at load is not picked up until something else reloads the solution.

`TrackedAnalyzers` (on `SolutionWorkspace`) covers build output the watcher cannot see. A load tracks every unresolved analyzer reference (a DLL that did not exist, typically an unbuilt generator project; its load diagnostic names the producing project, matched through `Project.OutputFilePath`/`CompilationOutputInfo`) and every analyzer DLL a project of the solution builds, each with the file stamp (write time + length, the shadow loader's key) taken before it was loaded. `InstanceRegistry.GetOrBeginAsync` calls `RoslynInstance.RefreshTrackedAnalyzersAsync` after the dirty check: a DLL whose stamp moved gets a fresh shadow-copied reference (load forced, failures kept as that entry's message) swapped into its consumer projects as an ordinary queued write, awaited so the same call reads it. This is probe-on-use, not watching, so it covers build output anywhere and builds that finish while the solution loads. A failed swap restores the stamps so the next call retries. `LoadDiagnostics` is computed: an unresolved DLL's message is listed only while the DLL is missing and was never attached.

Watcher errors are not ignored (`WatchDiagnostics`): an error that may have dropped events marks the instance dirty so the next use reloads it, and an error a reload cannot fix (the OS watch limit) is kept and listed by `get_solution_status` as `watchDiagnostic=`. Disk stale validation is a separate correctness layer. Fold transforms use the latest solution, but the current text-fold implementation reads disk text before queueing; do not assume it re-reads inside the queue. For concurrency work, test intervening edits and rebuilds explicitly.

## Semantic identity, conditional code and Razor

`SymbolResolver`, `SymbolSignature`, `SymbolAmbiguity` and `EnclosingDeclaration` centralize names, overload parsing, candidate rendering and enclosing declaration identity. Use them instead of ad hoc `ToDisplayString()` identities or string matching. Candidate strings must round-trip into the same tool and resolve the intended overload. The signature renderer progressively adds ref kinds and qualified parameter types when needed; parameter names/defaults and nullable spellings are handled by the parser. Preserve overload, generic, indexer and partial-declaration tests.

Name matching is exact-first: the strict fully-qualified comparison runs before a relaxed, segment-by-segment pass in which a written arity (`Box<T>`, ``Box`1``, `Box<>`) constrains the declared arity and an unwritten segment matches any. So a bare generic name resolves when unique, several arities report `error=Ambiguous` with one candidate per arity, and a non-generic of the same name wins (`SymbolSignature.Classify` reports which level matched; `SymbolResolver.FindRankedAsync` runs the two passes). `ProjectionService.ResolveAsync` holds every projection to the strictest level any of them reached, and `get_symbol`/`get_members` resolve through it — metadata is consulted only when no projection matched in source, with a type-only `accept` filter for the type-only tools. A source-declared symbol found by the metadata fallback (`GetTypeByMetadataName`, re-spelled through `SymbolSignature.MetadataNameOf`) is rendered from source, never reported `NotSupported`.

Local functions are named as members of their declaring member: `N.Outer.Type.Method.local`, and `N.T.M.outer.inner` for nested local functions. Roslyn gives them no qualified display name (`ToDisplayString()` is the bare `local`; the documentation ID flattens to `M:N.T.local`), so never use either as identity. `LocalFunctions` owns the rules:

- `NamedContainer` walks past lambdas/anonymous methods and maps accessors to their property/event. `ContainerChain` gives the outer-to-inner containers for outline nesting.
- `SymbolResolver.FullyQualifiedName` and `SymbolSignature.Of` build the name from that container. `Of` always renders the container's own parameter list (`N.T.M(int).local(string)`), so `KeyOf` and candidates stay unique across overloaded containers and round-trip.
- Any segment of a query may carry a parameter list. `SymbolSignature.TryGetContainer` splits at the last top-level dot, and `NameMatches` matches a local function's container recursively as a name in its own right, not by flattened text.
- Local functions are not in `SymbolFinder`'s declaration index. `FindByFullyQualifiedNameAsync` searches for them only when no ordinary symbol matched: it resolves the container name recursively, then scans that container's syntax (`FindInAsync`). A bare name scans the whole solution (`FindAllAsync`). This fallback is sound because C# forbids a nested type and a member of the same name in one type (CS0102), so a dotted name cannot mean both. Keep the fallback lazy: it walks syntax.
- `SymbolKindText` reports `localfunction`. `SymbolPlacement`, `EnclosingDeclaration` and `get_members` nest local functions under their containers.

`FindAllAsync` (the bare-name search) walks `project.Documents` and the project's source-generated documents, so local functions inside generated members are searchable.

Regression tests: `Morris.Roslynk.Tests/Features/LocalFunctions` against `TestFixtures/LocalFunctionSolution` (nested class, local-in-local, overloaded container).

`ProjectionService.BuildAsync` creates the base solution plus variants toggling each condition symbol that is uniformly defined or uniformly undefined across C# projects. Symbols with mixed definitions across loaded projects are skipped. **This is not exhaustive enumeration of combinations**; a branch needing multiple simultaneous toggles may remain uncovered. Resolve/query within each projection's own solution, then deduplicate using `ProjectionService.KeyOf` (the shared fully qualified signature with ref kinds). This key intentionally collapses identical qualified signatures across projects; it is not assembly-qualified identity.

`RenameSymbolTool` is a useful example of multi-projection editing: run semantic rename per projection, collect/deduplicate physical-file text changes by span, then apply the union to every matching document in the base solution. Preserve inactive-branch and multi-target consistency when adding similar operations.

Source-generated declarations resolve by name whether or not hand-written code mentions them: when the declaration search finds nothing (or the query is a bare name), `SymbolResolver` asks generator-bearing projects' compilations (`GeneratedDeclarations`: `GetSymbolsWithName` over source-generated trees) and runs the results through the normal `Expand`/`Matches` pipeline, so every name-based tool — and local functions and nested generated types — sees generator output; `SuggestAsync` proposes generated names too. `GetSymbolBodyTool` renders a source-declared symbol found by the metadata fallback from its `DeclaringSyntaxReferences` instead of reporting `NotSupported`. Write tools (`rename_symbol`, `rename_parameter`, `change_signature`) refuse symbols whose defining part is generated-only (`GeneratedSource.IsGeneratedOnly`) — `.g.cs` documents are never persisted, so the edit would silently no-op and break the build.

Razor has two representations: real `.razor`/`.cshtml` additional documents and generated C# made available as editable model documents by `RazorDocumentGenerator`.

- Workspace loading remaps analyzer references to a shadow-copy loader **before** requesting compilations/Razor augmentation. Otherwise generator DLLs in another project's `bin/obj` can be locked and prevent rebuilding them.
- Razor augmentation runs per project in dependency order (`GetTopologicallySortedProjects`): a project's generator discovers the components of the projects it references from their compilations, so those must be generated first. Only projects with `.razor`/`.cshtml` additional documents are augmented.
- `RazorGeneratorLoader` prefers the generator instance of the project's own (shadow-loaded) analyzer reference; when that is refused or absent it loads the SDK's DLL into an isolated per-file load context, never the default one (which can hold one Razor compiler per process).
- Razor augmentation runs the generator whenever one loads. Only when none does, it falls back to the pre-generated output of the last build (`RazorSnapshot`, located through `CompilationOutputInfo`, so it is per configuration/TFM and works for artifacts or custom intermediate layouts), minus orphans whose source is gone (matched source to hint name in flat and folder-preserved layouts; directive files claim their own output). Stale but nonorphan files are kept to preserve useful binding, so freshness is not guaranteed in that fallback, and it records no generator, so its Razor edits reload. A build's snapshot is rarely provably fresh anyway (MSBuild rewrites only changed outputs and never prunes orphans), so it is not preferred over the generator.
- The native Razor generator reference is removed and stays removed once Roslynk supplies generated documents (even when the generator crashed), preventing duplicate partial members and bindings to an immutable duplicate.
- `RazorGenerationState` (one per `SolutionWorkspace`, exposed as `SolutionWorkspace.Razor`) keeps each project's generator, last `GeneratorDriver`, generated documents by hint name and the Razor compiler's diagnostics. Regeneration hands the driver the project's compilation as the build would: without the previous generated documents and without any analyzer references, so the project's other source generators do not run on the generator's input as well as on the real compilation (in the build they run beside the Razor generator, not before it). The driver's own incremental cache skips component discovery when declarations are unchanged. It then updates only documents whose text changed, adding new ones in one batch. Generated documents of a multi-targeted project share one path per hint name across frameworks; duplicate detection is per project. `get_diagnostics` appends `RazorGenerationState.Diagnostics` (external-file locations in the Razor source) to the compiled diagnostics.
- Use `RazorMapping.GetDisplaySpan` for user-facing source positions. `RazorChangeMapper` maps pre-edit generated spans through `#line` directives, obtains Razor text from the captured solution, validates bounds and exact old text, and rejects unmappable/mismatched changes before writes.
- Rename keeps generated C# changes in memory while writing the corresponding additional documents. One generated document can map to several Razor files (including imports); duplicate/conflicting mapped edits need handling. Never write generated C# to disk as the rename result.
- Other tools that edit or take positions in `.razor`/`.cshtml` go through two seams:
  - `RazorSourceDocument` resolves a user path to the generated document and maps Razor positions into it. Each mapped position is verified by mapping it forward again. Action IDs store the Razor path, because generated paths mix separators.
  - `RazorGeneratedChangeFolder.FoldAsync` writes the result back region by region, not edit by edit, because formatting operations re-indent to the generated class and move whitespace across `#line` boundaries. Text outside regions may differ only in whitespace, otherwise the fold throws. Lines Roslyn formatted (space-indented) are re-based onto the file's indentation, and untouched lines are kept verbatim. The in-memory generated regions are rewritten to the reconciled Razor text, so a following operation still maps before the watcher rebuilds.
- Add new Razor-capable write tools through these two seams, and map `RazorMappingException` with `RazorGeneratedChangeFolder.ErrorFor`.
- Analyzers skip generated code, and the compiler never reports CS8019 there. `RazorUnusedUsings` therefore re-parses the generated document as ordinary code to find unused `@using` lines, and never edits `_Imports.razor`/`_ViewImports.cshtml`.
- Regression tests: `Features/RazorSupport` against `RazorSolution` and `CshtmlSolution`.

## Diagnostics and code actions

`DiagnosticsService` gets project compilations and optionally runs analyzers through `AnalyzerDriverFactory`, four projects at a time (each analyzer run is internally parallel). Source generators can affect compilation even when analyzer diagnostics are disabled. Preserve `project.AnalyzerOptions` (additional files/editorconfig) and isolation of analyzer failures.

Results are memoized per project (a `ConditionalWeakTable` keyed by `ProjectId`) against the inputs they depend on: the compilation's syntax trees (generated ones included) and options, the project's metadata and analyzer references, each referenced project's `GetDependentSemanticVersionAsync`, and for analyzer results the `AnalyzerOptions` reference. All are compared by reference except the versions. A project an edit did not touch is never recomputed, and neither is one whose dependencies changed only inside method bodies, although Roslyn forks its compilation (C# project references are compilation references). An analyzer run also fills the compiler-only result (its diagnostics tagged `Compiler`), and `DocumentDiagnosticsProvider` takes compiler diagnostics from the same memo, so no caller compiles a project twice. Any new input a project's diagnostics depend on must join the key.

`GetDiagnosticsTool` defaults to analyzers enabled, whereas the lower-level service defaults to false. Counts for errors/warnings/info/hidden are always returned; flags control details. It uses the queued diagnostics API and maps results against `DiagnosticsResult.Solution`. Private fixer-trigger IDs are removed from both counts and rendered diagnostics. Its `projectName`/`filePath`/`ids`/`maxSize`/`summaryOnly` filters are applied in the tool after the memoized result is produced, and must not enter the diagnostics cache key (the cache key stays `includeAnalyzers`).

`DocumentDiagnosticsProvider` is the shared code-action diagnostic path. It obtains the project's compiler diagnostics from `DiagnosticsService`'s memo, then filters to the document (needed for completion diagnostics such as CS8019). Analyzer work is narrowed to fixable, nonsuppressed rules, including hidden rules. It has a five-second analyzer cancellation budget and compiler-only fallback, a four-document task cache keyed by document ID and dependent semantic version, and one reusable analyzer driver keyed by project/version/analyzer set. Shared computation deliberately does not take a caller's cancellation token. Keep caches bounded and semantic-version-aware.

`CodeActionCatalog` discovers C# fix/refactoring providers from Roslyn feature assemblies; providers requiring unavailable imports are skipped. It maps the private unnecessary-imports trigger to public IDE0005. `CodeActionService` discovers actions and encodes path/span/kind/key into an opaque base64 JSON ID. Applying an ID re-discovers the action; do not retain Roslyn action objects across calls or assume discovery remains valid after an edit. Only an `ApplyChangesOperation` produces the changed solution for persistence. Check neighboring behavior when introducing support for a new provider or operation type.

## MCP contracts and adding tools

Engine registration is `ServicesRegistration.AddRoslynk` in `_ServicesRegistration.cs`; services are currently singletons. The served app adds one singleton per `[McpServerToolType]` class (`RoslynkEngineRegistration.AddRoslynkEngine`). Public tool classes carry `[McpServerToolType]`, with named methods, explicit tool annotations and parameter descriptions. These attributes are now the engine's own contract record (the engine tests and `MultiQueryCatalog` read them); MCP clients see what Nuru McpHost derives from the `[Operation]` contracts. Tool methods carry `[Description]` attributes containing their current per-tool guidance; `OperationContractTests` keeps each method's name, description, title and parameters equal to its operation's. Add shared dependencies to this registration and preserve thread safety for singleton state.

Each tool is also a typed operation in the same folder: a `public static partial class <Operation>` with a nested `Query` or `Command` (`IQuery` / `ICommand` of `OneOf<Response, SharedProblemDetails>`), a `Response`, and `[Operation("<mcp tool name>", Description = ...)]` whose description is the method `[Description]` text, moved and not reworded. Request properties are the MCP parameters (same names, `[Description]`s and defaults). `CancellationToken` stays off the request. Writes are commands and keep `checkOnly`; every other tool, including `open_solution` and `reload_solution`, is a query. The public MCP method only fills the request, calls the handler and renders. Success text is the outline the tool already built, carried on the response and emitted by an `IResponseRenderer<TResponse>`, the operation's public nested `Renderer` (`AddRoslynk` registers every one; the app's Nuru routes find it because it is public). A `SharedProblemDetails` renders to today's `error=` / `errorMessage=` / `candidate` / `stale` headers: `Type` is the error code, `Detail` is the message, and candidates, stale paths and any extra headers live in `Extensions`, in the original order, so the bytes do not change. `StaleWriteException` becomes a Stale problem inside the write handler (`Problems.FormatStale`), so every write tool reports it the same way. The app's handlers (`Morris.Roslynk.Cli/Handlers`) map an exception that escapes an engine handler to `Invalid` / `Faulted` with `ToolErrors.ToError` (the rule multi_query applies per operation) and rethrow cancellation. Each request class carries `[DisplayName]` (the tool title) and its `[Operation]`; never put Nuru attributes on engine contracts. Write tools' `destructiveHint` and every tool's `openWorldHint: false` are set by the app (`McpServerRegistration.CreateOptions`) from the operation kind, until TimeWarp.Contracts gives those hints a neutral home (timewarp-architecture 391).

A new or changed member type must round-trip through System.Text.Json, because Nuru binds `--json-args` and MCP arguments onto the engine's request type with that serializer (the app has no contract copy of its own; see Hosting and the CLI). Object and array members publish the JSON schema of their type; name nested JSON properties in lowercase with `[JsonPropertyName]` (`multi_query`'s `tool`/`arguments`, `apply_patch`'s `path`/`version`) and give them `[property: Description]`. Schema behavior is tested through the published MCP surface (`McpSurfaceTests`), not just reflection on method signatures.

Every paging tool takes `countOnly`: headers plus `count=` and one `count.<kind>=` per kind present, no body and no paging headers, with `startItem`/`maxSize` page limits ignored (`OutlineDescriptions.CountOnlyOutput` is the shared sentence; `get_symbol_body` counts lines, and `get_diagnostics`/`find_dead_code` keep their `maxSize` row/scan caps). `startItem=0` is page 1. A `filePath` resolves through `DocumentPathResolver` (exact, then a unique path suffix or file name, echoed as `resolvedPath=`; several matches are `Ambiguous`), and a `symbolName` may be a unique dotted-segment suffix (`resolvedSymbol=` on `get_symbol`/`get_symbol_body`).

Output is a compact text protocol: `key=value` headers, optional blank line and tab-indented outline. Booleans are `Y`/`N`; `status` is omitted for Ready. Use `OutlineBuilder`, `OutlineError`, `ChangedFilesOutline`, `FolderFiles`, `SymbolNode`, `ProjectName`, `SolutionRelativePath`, `ResponseBudget` (the server-wide ceiling: paging tools bound their `maxSize` by it, `ItemPaging` is the shared item pager every oversized result goes through, and `ResponseBudget.Fit` is the cut backstop for the tools that cannot page — get_symbol, find_definition, get_expression_info, get_solution_status) and `LineWindow.CountLines` (line counting for verbatim text) as appropriate. Sanitize header/free-text record fields so embedded newlines cannot corrupt framing. Source bodies returned verbatim must retain their original formatting. Tool descriptions sometimes show `#project`/`#path`; current `OutlineBuilder.Header` actually emits unprefixed keys. Trust implementation and contract tests when changing output.

Outline leaf standards (follow these in new and changed tools):

- Leaves are positional, comma-separated fields: `kind,name,loc[,extra...]`. A later field keeps its position, so when `loc` does not apply (a symbol declared in a referenced assembly) the field is present but empty (`method,get_Length,`, `method,WriteLine,,int`).
- Several values inside one field are pipe-delimited (`|`): multiple locations (`5:3|9:3`) and parameter types (`string|int`).
- A single value that itself contains a comma (e.g. `Dictionary<string, int>`, `Func<T, TResult>`) is single-quoted with `OutlineBuilder.Field`; never replace the comma or the quoting with another scheme.
- Parameter types are rendered with the shared `ParameterTypes.Of` (minimally qualified, nullable annotations kept, no `ref`/`out`/`in`). Where a tool shows them only to disambiguate overloads, emit them only when the symbol's own type declares more than one method of that name (inherited overloads do not count), and write `()` for the parameterless overload.
- Report symbols as declared: map a generic instantiation to its `OriginalDefinition` and a reduced extension call to its static declaration (`ReducedFrom`), so instantiations collapse and the parameter list matches `get_members`.
- Group symbols declared in a referenced assembly under a top-level bucket named for the assembly's simple name, as `get_callees` does with `<external:AssemblyName>` (`<external>` if unknown). `get_members` and the shared `SymbolPlacement` still use the older single `<metadata>` bucket.
- Do not spend effort sanitizing names that come from metadata (assembly, type or member names) against deliberately hostile assemblies; newline sanitizing is for free text such as messages and titles.
- Name new boolean parameters so their default is `false` (e.g. `excludeExternal = false`, not `includeExternal = true`).

For a read-only feature, follow the public-method/handler/core split exemplified by `GetSymbolTool`: the public method gets the instance, captures the model once, fills `GetSymbol.Query` and renders the handler outcome. The handler takes that pinned `SolutionModel`, the `RoslynInstance` and the request, and calls the internal core. The core accepts that model and uses it throughout. Do not reacquire current state from inside a core.

For a new read-only tool, first ask the user whether to include it in `multi_query`, as required above (no need to ask if they already explicitly said to add it). If included, update `MultiQueryOp` (in `MultiQueryOperation.cs`) and `MultiQueryCatalog.Entries` together, using the tool's name constant and the handler (`HandleAsync`) that accepts the request. Request property names and defaults must agree with the public method's parameters. `solutionId` stays on the request, and the batch supplies it: an operation argument named `solutionId` is an unknown key. The binder supplies `SolutionModel`, `RoslynInstance`, an optional slot `ResponseBudget` and cancellation itself, and binds the remaining arguments onto the request; callers cannot inject the pinned values. Unknown keys fail as `error=UnknownArgument` (the shared `UnknownArgument.Reject`, naming the valid arguments) rather than being silently ignored. Its supported coercions are string/bool/int/int? and string[] (a real JSON array or a JSON-array string, `JsonArrayArgument`); extend binder and schema tests deliberately if adding other types. The handler's `OneOf` outcome is rendered with the operation's `IResponseRenderer` (or the nested renderer when the provider has none) and `ProblemOutline` for problems. A target that returns `Task<string>` and takes no `[Operation]` request — an internal core, or a test stub — keeps the older parameter binder. An operation the caller's JSON cannot describe (unknown tool, missing tool, non-object arguments) is bound leniently by `MultiQueryOperationConverter` and reported in its own slot as `error=Invalid`, naming its index; the rest of the batch runs.

`MultiQueryTool` captures one model for every batch. Every operation executes — in parallel, cores being pure against the pinned snapshot — and each result is measured as its frame plus body; whole results are then delivered smallest-first (ties by request index, the count-optimal greedy) until the server-wide `ResponseBudget` (default 80,000 characters, read by the host from `Roslynk:MaxResponseChars` and registered as a plain value so the engine stays config-free) is filled, and delivered slots are emitted in request order. A slot is complete or absent — never cut — so a delivered slot's own body headers are the whole truth and may drive tool-level paging (`nextStartItem=`). Operations that did not fit become one `retry=<index>:<size>` header line in request order, each size the result's cost as a ratio of the echoed budget (which is net of the envelope's own framing) rounded up to 0.1; the model plans continuations from those ratios (≥ 1.0 re-send alone, it pages; Σ ≤ 1.0 fits one batch). The batch limit is not a constant: a batch whose worst-case retry line cannot fit the budget is refused with `error=Invalid` before anything executes. A random boundary frames verbatim bodies, and the delimiter count is checked against the delivered frames plus terminator. Cores declare a binder-supplied `ResponseBudget?` — null from the batch (render whole; the batch drops oversized results) and the real budget stand-alone (an oversized result then pages via `ItemPaging`) — plus explicit `startItem`/`maxSize`, which page in both paths (a continuation re-sending one oversized operation relies on that). A failing operation is delivered as its normal `error=` block and can be dropped like any oversized result. Continuations use `expectSnapshot` to reject a different publication generation before any operation executes. Diagnostics, lifecycle, writes and code-action discovery are not in the current batch catalog.

When extending a tool: preserve the response/error contract, add meaningful behavior tests, add schema/composition tests for public changes, keep the consumer skill aligned with the change (the relevant C# tool descriptions, plus `SKILL.md` when routing changes), update README where affected, and record the feature change under `# Unreleased` at the top of `releases.md`. A similar existing tool is a starting point, not proof that it handles every concurrency or Razor case.

## Hosting and release touchpoints

Roslynk runs as one TimeWarp.Nuru served app (task 005). `roslynk serve` (Nuru Daemon, `AddServeRoute(autoStart: true, idleTimeoutSeconds: 3600)`) is the shared server: it listens on a per-user Unix domain socket named for its build (`roslynk-<8 hex>.sock`, timewarp-nuru 508-017; `NURU_DAEMON_SOCKET` overrides it; no TCP port), runs calls concurrently, each with its own output, exit code, working directory and cancellation token, and stops after an hour without calls. Every operation call of the CLI and every MCP `tools/call` from `roslynk stdio` forwards to it, so all of them share one warm `InstanceRegistry`. Keep protocol stdout free of ordinary logs. Startup, tracing and observability changes belong in the app's `Hosting/`; semantic behavior belongs in the engine.

- **Idle eviction.** Kept beside Nuru's idle stop, not mapped onto it: `RoslynkEngine` closes a solution nobody used for `Roslynk:IdleEvictionMinutes` (default 30, checked every `Roslynk:EvictionCheckMinutes`), so a server kept busy by one solution still releases the others; the process itself stops after 3600 s without any call.
- **Engine composition.** `Hosting/RoslynkEngine.cs` is a Nuru singleton that composes the engine (`AddRoslynk`, the tools, eviction, and OTLP export of the engine's `Morris.Roslynk` traces and metrics when `OTEL_EXPORTER_OTLP_ENDPOINT` is set) on first use. Nuru's generated DI builds a singleton on first resolution (timewarp-nuru 508-007), so a forwarded call, `--capabilities` or a usage error never constructs it; the composition stays lazy inside it as well, so constructing the type is free of engine work either way: a forwarded call and `--capabilities` load no Roslyn or MSBuild (`ProcessIsolationTests`). Settings come from Nuru's configuration (environment, `appsettings.json` beside the executable, read without a file watch, `--Roslynk:Key=value`), read once into `Hosting/RoslynkSettings` (`MaxResponseChars`, `LoadWaitSeconds`, `IdleEvictionMinutes`, `EvictionCheckMinutes`; nullable, with the defaults in its `Effective*` members) when the engine starts. The package ships a commented `appsettings.json.example` beside `roslynk`.
- **Forwarding.** `Hosting/RoslynkForwarder.cs` wraps Nuru's daemon client: every call is forwarded with a forced start (Nuru alone would run an operation in the CLI process when a start fails), and a call that got no answer from a server of this build becomes exit 69 with one line. `--no-daemon` still runs a call in the CLI process. Each build has its own default socket, so two builds (a `dnx TimeWarp.Roslynk -- stdio` package-cache copy beside a global `roslynk`, or a local build beside the installed tool) run two warm servers side by side and never stop each other's server or cancel its calls. On a socket two builds share (`NURU_DAEMON_SOCKET`), the other build's server is left running and the call fails with exit 69 and Nuru's one line naming both builds. `roslynk serve --status` shows the build serving and lists other builds' servers; an unused one stops on its idle timeout.
- **MCP.** `Hosting/StdioCommand.cs` is the local-only `stdio` route: it starts the server if needed (one line and exit 69 when it cannot), then runs Nuru McpHost over the catalog minus `stdio` itself, with the server instructions and annotations from `McpServerRegistration`. McpHost returns a problem as an error result (`isError`) whose text is the `error=` outline; success text is the outline. A binding failure (missing, unknown or mistyped argument) and an exception that escapes a handler render through the same `ProblemRenderer` as `error=Invalid` / `error=Faulted`, in process and when forwarded (timewarp-nuru 508-018).
- **Aspire.** The AppHost runs `roslynk serve` with `NURU_DAEMON_SOCKET=roslynk-apphost.sock`, so an installed roslynk's server (another build) is left alone; point a development client at it with the same variable. `installer/run.sh` runs `dotnet run ... -- serve`.

The release workflow `.github/workflows/workflow.yml` triggers on numeric version tags (no `v` prefix), runs the full solution tests in Release on Linux, packs `Morris.Roslynk.Cli` (the `TimeWarp.Roslynk` tool, command `roslynk`) using the tag version, and pushes it to TimeWarpEngineering's GitHub Packages feed (`https://nuget.pkg.github.com/TimeWarpEngineering/index.json`, a private package linked to this repository) with the run's `GITHUB_TOKEN` (`packages: write`). A `feature/**` pull request runs the tests only. Nothing goes to nuget.org from any trigger: `Roslynk` there is Peter Morris's upstream package, and the fork must not publish it (task 007, fork issue #11). Tagging is a human release step. The package runs on `Microsoft.NETCore.App` alone (no ASP.NET Core). Preserve cross-platform file/path behavior even when developing on Windows. Ordinary feature implementation does not require starting a server, publishing a package or tagging a release.

## Hosting and the CLI

`Source/App/Morris.Roslynk.Cli` (assembly `roslynk`) is the `roslynk` command and the `TimeWarp.Roslynk` .NET tool package. It is one TimeWarp.Nuru app. Its 29 operation commands are derived from the `[Operation]` request classes: the route is the operation name, and each request property is one option under its declared (camelCase) name. Descriptions, titles and defaults come from the same attributes the MCP tools publish. Beside them are `stdio` (the MCP server) and Nuru's built-in `serve` (`--status`, `--stop`).

- **Contracts from the engine assembly.** `[assembly: NuruEndpointAssembly(typeof(GetSymbol.Query))]` in `Program.cs` adds every public `[Operation]` request of the engine assembly to `DiscoverEndpoints()` (timewarp-nuru 508-013); the app compiles no contract source of its own and references the engine plainly. The engine grants it `InternalsVisibleTo`. Nuru reads these types from metadata, so: an option's default comes from its `[DefaultValue]` (keep it equal to the initializer, which is what runs; `[DefaultValue(null)]` shows no default in `--capabilities`, which McpHost's schema leaves out anyway), a caller must supply exactly the `required` members, and a response's nested `Renderer` must be `public` (Nuru ignores an internal renderer in a referenced assembly). The engine is not a TimeWarp.Mediator graph member: the handlers live in the app, whose generated mediator registers them, and marking the engine `[MediatorAssembly]` would make every generator host that references it (the CLI tests) report TWM001 for its requests. A forwarded call loads the engine assembly for the request types but nothing past them, so the contract types (and the types they declare) must stay free of Roslyn, the engine's DI and other engine types; `ProcessIsolationTests` fails if Roslyn or MSBuild loads. JSON attributes in contracts must be AOT-friendly: use `JsonStringEnumConverter<TEnum>`, not the non-generic converter. Nuru's generated JSON context reports SYSLIB1034 for the non-generic one, and that is an error here.
- **Handlers.** `Handlers/OperationHandlers.cs` has one thin handler per operation, so the generated mediator has a handler for every route (a missing one is TWM001 / NURU_H008, errors under warnings-as-errors). A handler resolves a relative `solutionId`/`solutionPath` on the request Nuru bound against the caller's directory (`OperationHandler.FromCaller`, `NuruCallContext.GetFullPath`) and calls the engine tool's `HandleAsync` with it: reads with the pinned `SolutionModel`, `RoslynInstance` and `ResponseBudget`, writes, code actions, diagnostics and multi_query with the request and the call's cancellation token. The engine outcome travels as its outline text: `ProblemOutline.TryParse` turns `error=` text into a `SharedProblemDetails` with its exit code as `Status`, and a success over the budget is cut with `ResponseBudget.Fit` (except multi_query). Each call runs in a `Morris.Roslynk` span named after its operation.
- **Output.** `UseVerbatimRendererOutput()` writes renderer text unchanged (no added newline). Success goes to stdout through each contract's nested `Renderer`; a problem goes to stderr through `Output/ProblemRenderer` (`IResponseRenderer<SharedProblemDetails>`, the `error=` outline), and Nuru exits with `SharedProblemDetails.Status`.
- **Exit codes** (`Output/ExitCodes`, carried in `SharedProblemDetails.Status`):

  | Code | Meaning |
  | --- | --- |
  | 0 | Success |
  | 1 | Usage or binding error reported by Nuru: usage text, or (with `UseProblemRendererForErrors()`) an `error=Invalid` outline on stderr for an option value or `--json-args` member that does not bind. It stays 1, apart from the engine's `Invalid` (2), because the call never reached a tool |
  | 2 | `Invalid` |
  | 3 | `NotFound` |
  | 4 | `Ambiguous` |
  | 5 | `Indexing` |
  | 6 | `Stale` |
  | 7 | `Conflict` |
  | 8 | `NotSupported` |
  | 9 | `Faulted` |
  | 10 | `Truncated` |
  | 11 | `UnknownArgument`: an argument the operation does not declare. `multi_query` reports it per operation inside a successful batch; a call's own unknown option or `--json-args` key is Nuru's binding error (exit 1, `error=Invalid`) |
  | 69 | Server unavailable: no server of this build runs and none could be started, another build's server holds a shared socket, or the server stopped answering during the call (one line on stderr) |
  | 70 | An `error=` code `ExitCodes` does not know |

  Keep this table, `ExitCodes` and the README table in step when an error code is added.
- **Groups.** Every operation declares exactly one group on its own `[Operation(..., Group = "...")]` (TimeWarp.Contracts `OperationAttribute.Group`), and nowhere else: no Nuru attribute, no `[NuruRouteGroup]` and no app-side map. Nuru reports it as the route's `groupPath` without prefixing the route, so the command stays the tool name, and the MCP schema does not carry it. The five groups are `symbols` (get_symbol, get_members, get_symbol_body, find_definition, search_symbols, get_expression_info, get_type_hierarchy, find_implementations), `references` (find_references, get_callers, get_callees, find_reads, find_writes, find_dead_code, find_dead_conditionals), `solution` (open_solution, get_solution_status, reload_solution, get_diagnostics, get_code_actions), `edit` (the write tools: apply_code_action, apply_code_fix, extract_method, change_signature, rename_symbol, rename_parameter, remove_unused_usings, apply_patch) and `batch` (multi_query). `roslynk --capabilities --group-filter <group>` lists one group; `stdio` is ungrouped and drops out. `CapabilitiesContractTests` pins each route's group.
- **Adding an operation.** The engine assembly's endpoint opt-in picks up its public request class; keep the contract Roslyn-free, give every defaulted member a matching `[DefaultValue]` and make its `Renderer` public. Give its request `[DisplayName]`, declare one of the five groups as `Group` on its `[Operation]`, add its handler line to `Handlers/OperationHandlers.cs` (and a sample for any new member type in `HandlerTests.SampleOf`), and add it to `ExpectedGroups` in `CapabilitiesContractTests`.
- **Tests.** `Morris.Roslynk.Cli.Tests` runs the built command as a process, each test class on a socket of its own (`ServerSocket`, a served Simple fixture in `ServedSolution`). It checks the catalog and the MCP tools against the engine's contracts, stdout/stderr bytes and exit codes, self-start and exit 69, concurrency, cancellation and the assemblies a CLI call loads. `HandlerTests` reference the app under the alias `app` for the caller-path, outcome mapping and cancellation units.
